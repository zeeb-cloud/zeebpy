# Migrations

Zeeb provides autogenerated, numbered migrations — no Alembic config files, no revision hashes, just clean numbered Python files.

## Overview

Migrations track changes to your models and apply them to the database. The workflow is:

1. **Make changes** to your models
2. **Generate migration** with `makemigrations`
3. **Apply migration** with `migrate`

## Getting Started

### Create First Migration

After defining models, generate the initial migration:

```bash
python manage.py makemigrations
```

Output:
```
Checking for model changes in installed apps:
  - blog
  - users

Migrations for 'all apps':
  0001_initial.py
    - Create model Author
    - Create model Post
```

`makemigrations` creates the `migrations/` directory automatically, so `init`
is rarely needed. Run `python manage.py init` only when you want the directory
(and its `.gitkeep`) created up front — it is idempotent. Migration files live
**flat** in `migrations/`, not under a `versions/` subdirectory.

### Apply Migrations

```bash
python manage.py migrate
```

Output:
```
Running migrations:
  Applying 0001_initial... OK
```

## Commands

### makemigrations

Generate migrations from model changes.

```bash
# Generate for all apps
python manage.py makemigrations

# Generate with custom name
python manage.py makemigrations -n "add user profile"

# Generate empty migration (for manual edits)
python manage.py makemigrations --empty

# Check for pending changes (CI/CD) — exits 1 if changes are detected, no file written
python manage.py makemigrations --check

# Preview what would be generated without writing any files
python manage.py makemigrations --dry-run
```

**Options:**
| Option | Description |
|--------|-------------|
| `-n, --name` | Migration name/description |
| `--empty` | Create empty migration |
| `--check` | Exit with status 1 if model changes are detected. No file is written. Ideal for CI pipelines to enforce committed migrations. |
| `--dry-run` | Show what migration would be created without writing any files. |

### migrate

Apply migrations to the database.

```bash
# Apply all pending migrations
python manage.py migrate

# Apply to specific migration
python manage.py migrate 0001

# Roll back all migrations
python manage.py migrate zero

# Rollback N migrations
python manage.py migrate --rollback 1

# Mark as applied without running
python manage.py migrate --fake

# Skip initial migration when tables already exist (adopting migrations in existing project)
python manage.py migrate --fake-initial

# Show what would be applied without running anything
python manage.py migrate --plan
```

**Options:**
| Option | Description |
|--------|-------------|
| `migration` | Target migration: a full name, or a unique prefix such as `0003` (optional) |
| `--rollback N` | Roll back N migrations |
| `--fake` | Mark as applied without executing |
| `--fake-initial` | Skip the first migration if its tables already exist |
| `--plan` | Print the list of migrations that would run, without executing them. It is checked like the real run (with `--fake` too) and refuses what the real run would refuse |

A target that matches no migration — or more than one — is refused with
`UnknownMigrationError` (`file_not_found` with `--json`), and nothing runs.
Afterwards exactly the migrations up to and including the target are applied:
later ones are unapplied (newest first), missing earlier ones applied.

**Order.** Migrations are applied in **dependency order** — a topological sort of
their `dependencies`, file names breaking ties — not merely by file name. A
dependency cycle is refused. So is an *inconsistent history*: a migration that is
recorded as applied while one of its dependencies is not. If the missing changes
are already in the database, `migrate <that migration> --fake` repairs it: it
records only the unapplied migrations up to that one, and the error lists them.

**One at a time.** `migrate` holds a database-wide lock while it plans and
applies — a PostgreSQL advisory lock, MySQL `GET_LOCK`, or on SQLite an OS lock on
a `<database>-migrate.lock` file beside the database — so replicas that all run
`migrate` on startup apply each migration once. Every one of these locks is
released when the process exits.

```bash
python manage.py showmigrations
```

Output:
```

```

- `[X]` - Applied
- `[ ]` - Pending

### squashmigrations

Squash a range of migrations into a single optimized file.

```bash
# Squash migrations 0001 through 0005 into one file
python manage.py squashmigrations 0001_initial 0005_add_views

# With a custom name
python manage.py squashmigrations 0001_initial 0005_add_views -n "initial_to_add_views"

# Skip the optimizer (keep all operations as-is)
python manage.py squashmigrations 0001_initial 0005_add_views --no-optimize
```

**Options:**
| Option | Description |
|--------|-------------|
| `start` | First migration in the range (inclusive) |
| `end` | Last migration in the range (inclusive) |
| `-n, --name` | Name for the squashed migration file |
| `--no-optimize` | Disable the optimizer — keep all operations |

The squashed file records the replaced migrations in its `replaces` attribute
(and a header comment lists them). The executor treats those originals as
superseded — it skips them when applying and marks them applied automatically
when the squashed migration runs — so the squashed file and the originals can
coexist safely without applying any operation twice. After the squashed
migration has been deployed everywhere, the original files may be deleted.

How a database meets a squash depends on how many of the originals it has:

- **None** (a fresh database): the squash runs, and records the originals too.
- **All**: the squash only records itself; nothing re-runs.
- **Some**: the squash cannot be used — its operations would re-run on top of a
  half-built schema — so the **remaining originals** are applied one by one, and
  the squash is recorded once they all are. Their files must still be on disk.

While the original files exist, a database can also be moved *into* a squash:
`migrate --rollback 1` after a squash unapplies only its last original, and any
original is a valid `migrate` target. Once the originals are deleted the squash
is one step. A dependency on a replaced migration means the squash, so the
squashed file may sit anywhere in the directory listing; it is numbered after the
range, or after the last migration when a later migration already holds the next
number (numbers stay unique, so a prefix such as `0003` names one file).

`RunPython` functions defined in the squashed files are copied into the new file,
along with the module-level helpers, constants and imports they use — default
argument values included — renamed when two files define the same name. Their
type annotations are left out of the copy. A range containing a migration that overrides
`pre_migrate`/`post_migrate` is refused — a squash cannot carry those hooks over
— and a range containing a non-atomic migration produces a non-atomic squash.

## Migration File Format

Migration files are clean Python with a `Migration` class:

```python
# migrations/0001_initial.py
"""Create model Post

Generated by Zeeb ORM on 2024-01-15 12:34
"""

import sqlalchemy as sa
from zeeb_orm.migrations import Migration, operations


class Migration(Migration):

    initial = True

    dependencies = []

    operations = [
        operations.CreateModel(
            name='Post',
            table='posts',
            columns=[
                sa.Column('id', sa.Uuid(), nullable=False),
                sa.Column('title', sa.String(200), nullable=False),
                sa.Column('content', sa.Text(), nullable=False),
                sa.Column('created_at', sa.DateTime(), nullable=True),
            ],
            primary_key=['id'],
        ),
    ]
```

### Migration class options

| Attribute | Default | Description |
|-----------|---------|-------------|
| `initial` | `False` | Mark this as the initial migration |
| `dependencies` | `[]` | List of migration names this depends on |
| `atomic` | `True` | Wrap all operations in a single database transaction |

### Pre/post migrate hooks

Override `pre_migrate` and/or `post_migrate` on your `Migration` class to run
custom code before or after the migration's operations execute:

```python
class Migration(Migration):

    dependencies = ['0002_add_slug']

    operations = [
        operations.AddField(
            model_name='Post',
            table='posts',
            name='slug',
            column=sa.Column('slug', sa.String(200), nullable=True),
        ),
    ]

    def pre_migrate(self, connection):
        """Called before operations run."""
        print("About to add slug column…")

    def post_migrate(self, connection):
        """Called after operations run (populate data, etc.)."""
        from sqlalchemy import text
        connection.execute(text(
            "UPDATE posts SET slug = LOWER(REPLACE(title, ' ', '-')) WHERE slug IS NULL"
        ))
```

### Non-atomic migrations

Set `atomic = False` to run outside a transaction — required for some DDL
statements that cannot run inside a transaction, e.g.
`CREATE INDEX CONCURRENTLY` on PostgreSQL. The operations then run with the
connection in autocommit mode: each statement commits on its own, so a failure
part-way leaves the earlier statements applied.

On MySQL every migration behaves this way for its DDL: MySQL commits implicitly
around each `CREATE`/`ALTER`/`DROP`, so a migration that fails part-way leaves its
earlier schema changes in place (and unrecorded). Keep MySQL migrations small, or
make them safe to re-run.

```python
class Migration(Migration):

    atomic = False  # Cannot run inside a transaction

    operations = [
        operations.RunSQL(
            sql="CREATE INDEX CONCURRENTLY idx_posts_slug ON posts (slug)",
            reverse_sql="DROP INDEX IF EXISTS idx_posts_slug",
        ),
    ]
```

### Available Operations

| Operation | Description |
|-----------|-------------|
| `CreateModel` | Create a new database table |
| `DeleteModel` | Drop a database table |
| `AddField` | Add a column to an existing table |
| `RemoveField` | Remove a column from a table |
| `AlterField` | Change a column's type, nullable, etc. |
| `RenameModel` | Rename a table |
| `AlterModelTable` | Rename a model's table (`Meta.table_name` changed), keeping its rows |
| `RenameField` | Rename a column |
| `AddIndex` | Create an index |
| `RemoveIndex` | Drop an index |
| `AddConstraint` | Add a named constraint (unique, check, …) |
| `RemoveConstraint` | Drop a named constraint |
| `RunSQL` | Execute raw SQL |
| `RunPython` | Execute a Python callable |

#### Reversibility

Unapplying a migration (`migrate <earlier>`, `migrate zero`, `--rollback N`)
runs each operation's reversal. An operation that cannot be reversed —
`RunSQL` without `reverse_sql`, `RunPython` without `reverse_code`,
`RemoveField` without `field`, `RemoveIndex` without `columns`,
`RemoveConstraint` without `constraint`, or a `DeleteModel` that does not record the dropped
table's columns — makes the rollback refuse **before anything runs**, with an
`IrreversibleError` naming the migration and operation. Nothing is ever
"reversed" by silently doing nothing. When no reverse step is needed, say so:

```python
operations.RunSQL("UPDATE posts SET slug = id", reverse_sql=operations.RunSQL.noop)
operations.RunPython(populate, reverse_code=operations.RunPython.noop)
```

`migrate --fake` records a rollback without running anything, for the rare
case where the schema was already put back by hand.

`makemigrations` writes `DeleteModel` with the dropped table's columns,
primary key and unique constraints (as the earlier migrations declared them)
and `RemoveIndex` with the index's columns, and `RemoveConstraint` with the
constraint itself, so all three reverse: the table, index or constraint is
recreated. Rows a `DeleteModel` dropped are not restored.

#### RenameModel

```python
operations.RenameModel(
    old_name='Post',
    new_name='Article',
    old_table='posts',
    new_table='articles',
)
```

Reversal: renames back to the original table name.

#### AlterModelTable

```python
operations.AlterModelTable(
    name='Post',
    old_table='blog_posts',
    new_table='posts',
)
```

What `makemigrations` writes when a model keeps its name but its
`Meta.table_name` changes: the table is renamed, rows included. Reversal:
renames it back.

#### RenameField

```python
operations.RenameField(
    model_name='Post',
    table='posts',
    old_name='body',
    new_name='content',
)
```

Reversal: renames back to the original column name.

#### RemoveField (with reversal)

Pass the `field` argument to enable reversal (the column can be re-added on
rollback):

```python
operations.RemoveField(
    model_name='Post',
    table='posts',
    name='legacy_id',
    field=sa.Column('legacy_id', sa.Integer(), nullable=True),
)
```

Without `field`, the operation is irreversible.

#### AlterField (with reversal)

Pass `old_column_type`, `old_nullable` and/or `old_server_default` to enable
reversal:

```python
operations.AlterField(
    model_name='Post',
    table='posts',
    name='views',
    column_type=sa.BigInteger(),
    old_column_type=sa.Integer(),  # needed for reversal
)
```

`None` means "unchanged" for every argument. To drop a server default pass
`server_default=operations.NO_DEFAULT`; for a column that had none,
`old_server_default=operations.NO_DEFAULT`. A string is a literal value
(`server_default="0"`), `sa.text("now()")` is SQL. Any further keyword argument
(`existing_nullable=False`, …) is handed to Alembic's `alter_column` — on MySQL,
restating a column needs the parts that are not changing.

#### AddConstraint / RemoveConstraint

```python
operations.AddConstraint(
    model_name='Post',
    table='posts',
    constraint=sa.UniqueConstraint('slug', name='uq_posts_slug'),
)

operations.RemoveConstraint(
    model_name='Post',
    table='posts',
    name='uq_posts_slug',
    constraint=sa.UniqueConstraint('slug', name='uq_posts_slug'),  # for reversal
)
```

Without `constraint`, `RemoveConstraint` is irreversible. `makemigrations`
always records it.

### Auto-detection

Zeeb compares your current model definitions against the **state described by existing migration files** (not the live database). This means:

- Running `makemigrations` multiple times without model changes produces no duplicate migrations
- You don't need to apply migrations before generating new ones
- Changes are detected reliably regardless of the database state

Zeeb auto-detects these changes (all generated operations are reversible).
Models with `Meta.managed = False` are left out: no operation is generated for
their tables, and test schemas (`temporary_database`, the generated `db`
fixture) do not create them either.

- **Tables**: Create, drop, rename — a model that keeps its class name but
  changes `Meta.table_name` gets an `AlterModelTable`, not a drop and a create
  (which would lose every row); any other change to it is detected alongside
- **Columns**: Add, drop, alter type — foreign-key and `unique=True` fields
  included
- **Nullability**: Changes to nullable
- **Server defaults**: Changes to a column's `server_default` — removal included
  (`server_default=operations.NO_DEFAULT`): a server default the models do not
  declare is dropped
- **Indexes**: Create, drop
- **Unique constraints**: Add, drop — including unnamed ones (what `unique=True` on a column produces), which are given a deterministic `uq_{table}_{cols}` name

Adding or removing a `ForeignKey` *field* is an `AddField` / `RemoveField`
carrying the reference. Changing the foreign-key constraint of a column that
stays (altering `on_delete`, pointing it elsewhere) is **not** auto-detected —
write a manual migration for that. On SQLite, adding a column with a foreign
key, a `unique=True` column or a `NOT NULL` column, dropping any column, and
column and constraint alterations are applied via Alembic batch mode
(`batch_alter_table`), which rebuilds the table via copy-and-swap (SQLite's
`ALTER TABLE` cannot add a constraint or drop a column a constraint uses);
migrations therefore run with SQLite's foreign-key enforcement switched off, so
dropping the old copy of a table never cascades into the rows that reference
it. A `unique=True` column added to an existing table gets the constraint
`uq_{table}_{column}` on every database, the name `CreateModel` gives it.

**Model names.** Operations on a table name the model that declares it; a
table no model declares any more (one being dropped) is named as the
migration that created it named it, never guessed from the table name.

**Order.** Operations are written so each runs after what it depends on: a
foreign key to a table, and a table that references it, are removed before
that table is dropped; a table is created before anything references it; a
renamed table is renamed before anything uses its new name. Rollback runs a
migration's operations in reverse, so it gets the reverse order — the table
comes back before the key that points at it. `squashmigrations`' optimizer
never moves an operation past one that touches the same table.

**Renamed fields.** A field removed while another with the same definition is
added on the same model looks like a rename, but it is written as
`RemoveField` + `AddField`, which drops the column and its data.
`makemigrations` warns about every such pair (and lists it under
`possible_renames` with `--json`); `makemigrations --accept-renames` writes a
`RenameField` for them instead, keeping the data.

**State replay.** The state the models are compared against is rebuilt by
replaying the migration files into an in-memory SQLite database, in the order
`migrate` applies them to a fresh database (a squash in place of the migrations
it replaces). If a schema operation fails to replay, `makemigrations` stops with
an error instead of comparing against a wrong state. `RunPython` is not run
during replay and `RunSQL` that SQLite cannot execute is skipped — both are
reported.

**Declared, not reflected.** A column's type, nullability and server default are
compared against what the migration files *declare*, not against what SQLite
reflects — SQLite cannot tell `DateTime` from `DateTime(timezone=True)`, but
PostgreSQL can, and a migration has to be right on every database. Types are
compared by the DDL they produce on SQLite, PostgreSQL and MySQL. So a project
whose older migration files lost a type argument gets an `AlterField` that
restores it, and the `old_column_type` an `AlterField` records for its rollback
is the declared type (a `Uuid`, not SQLite's `CHAR(32)`).

**Lossless files.** Operations are written from their constructor arguments —
every type argument (`timezone=True`, `Enum` values, `ARRAY` item types), dialect
types with their import (`from sqlalchemy.dialects import postgresql`),
`reverse_sql=RunSQL.noop`, `reverse_code=` — and each file is checked before it
is written: it must compile, import and load back into the same operations, and
each type must evaluate to one with the same DDL. A value that cannot be written
faithfully (a type defined inside a function, a lambda, a computed column) raises
`MigrationSerializationError` and **no file is written**: a broken migration file
would break every later `migrate` and `makemigrations`, which import them all.
A file that does not load anyway (edited by hand) raises `MigrationLoadError`
(a `MigrationError` and an `ImportError`) naming the file.

**Tracking table.** Applied migrations are recorded in `zeeb_migrations`,
created through SQLAlchemy so its auto-increment key is right on every
backend (SQLite, PostgreSQL, MySQL).

### ManyToMany Through Tables

Auto-created `ManyToMany` join tables (named
`"{source_table}_{field_name}"`, or the field's `db_table`) live in the
shared metadata next to regular model tables. The autodetector sees a new
M2M field as a plain **add_table** diff and generates a `CreateModel`
operation for the join table — there is no dedicated M2M operation. The
table contains the two `*_id` foreign-key columns (`ON DELETE CASCADE`)
and a unique constraint over the pair.

Custom `through=` models are ordinary models and migrate like any other
table.

## Common Workflows

### Adding a Field

```python
# 1. Add field to model
class Post(Model):
    title = fields.CharField(max_length=200)
    content = fields.TextField()
    views = fields.IntegerField(default=0)  # New field
```

```bash
# 2. Generate migration
python manage.py makemigrations -n "add views to posts"

# 3. Apply
python manage.py migrate
```

#### Adding a NOT NULL column

A `null=False` field cannot simply be appended to a table that already has
rows — there is no value for them. The framework handles this when the
migration is made and when it is applied:

- **`auto_now` / `auto_now_add` fields** (`DateTimeField`, `DateField`).
  `makemigrations` writes `AddField(..., backfill=sa.func.current_timestamp())`
  (`current_date()` for a `DateField`): existing rows get the time the
  migration runs. The column is added with that SQL `DEFAULT`, which is then
  dropped again on every database (SQLite included, by rebuilding the table),
  so the schema matches the migration files.

- **The field has a scalar `default`.** The default is emitted as a SQL
  `DEFAULT` on the `ADD COLUMN`, so the database backfills existing rows in the
  same statement. The backfill `DEFAULT` is a means of adding the column, not
  part of the schema the migration declares: on PostgreSQL and MySQL it is
  dropped again straight away, so the database matches the migration files.
  SQLite cannot drop a default without rebuilding the table, so there it stays —
  unused by the ORM, which always writes the column, and invisible to
  `makemigrations`, which compares against the declared schema.
- **Anything else** (no default, or a callable one). `makemigrations` refuses
  — it raises `NotNullFieldError` (`--json`: `success: false`, the fields
  under `data.fields`) and **writes no file**, since that migration could
  never be applied to a table with rows (on SQLite, not even to an empty one):

  ```
  Cannot add the NOT NULL field(s) Post.views to existing table(s): rows
  already there would have no value. Give each field null=True or a static
  default (a callable default cannot fill existing rows), then re-run
  makemigrations.
  ```

  When the field looks like a renamed one, the message also points at
  `--accept-renames`. A hand-written `AddField` with nothing to fill the rows
  still fails at `migrate` with `MigrationError`, before the column is added.

A callable default (`default=uuid4`) is not a scalar and cannot be pushed into
SQL. For those, use the three-step pattern: add the column as nullable,
backfill it in a data migration, then alter it to `NOT NULL`.

### Data Migrations

For data transformations, create an empty migration:

```bash
python manage.py makemigrations --empty -n "populate slug from title"
```

```python
# Edit the generated migration
import sqlalchemy as sa
from zeeb_orm.migrations import Migration, operations


class Migration(Migration):

    dependencies = ['0002_add_slug']

    operations = [
        operations.RunSQL(
            sql="""
                UPDATE posts
                SET slug = LOWER(REPLACE(title, ' ', '-'))
                WHERE slug IS NULL
            """,
            reverse_sql=operations.RunSQL.noop,  # nothing to undo on rollback
        ),
    ]
```

### Adding a Relationship

```python
# 1. Add ForeignKey
class Post(Model):
    title = fields.CharField(max_length=200)
    author = fields.ForeignKey(
        "Author",
        on_delete="CASCADE",
        null=True,  # Allow null for existing rows
    )
```

```bash
# 2. Generate and apply
python manage.py makemigrations -n "add author to posts"
python manage.py migrate
```

### CI/CD — Enforcing Committed Migrations

Add a step in CI to ensure all model changes have a corresponding migration:

```yaml
# .github/workflows/ci.yml
- name: Check for uncommitted migrations
  run: python manage.py makemigrations --check
```

This exits with status 1 when any model changes are not yet represented by a
migration file, failing the pipeline.

### Squashing Old Migrations

After many iterations, squash migrations 0001–0010 into one file:

```bash
python manage.py squashmigrations 0001_initial 0010_add_comments
```

The optimizer automatically combines operations (e.g. `CreateModel` + `AddField`
on the same table become a single `CreateModel`), resulting in a compact file.

## Migration Tracking

Applied migrations are tracked in the `zeeb_migrations` table in your database. This table is automatically created when you first run `migrate`. `showmigrations` reports a squash as applied when every migration it replaces is, even before `migrate` has recorded it.

```sql
-- The tracking table
SELECT * FROM zeeb_migrations;
-- id | name              | applied_at
-- 1  | 0001_initial      | 2024-01-15T12:34:56
-- 2  | 0002_add_profile  | 2024-01-16T09:00:00
```

## Custom User Models

When using a custom user model via `AUTH_USER_MODEL`, the migration system
automatically handles the `UserPermission` table.  Its foreign key points to
whichever user model is configured — no extra setup needed.

```python
# settings.py
AUTH_USER_MODEL = "apps.accounts.CustomUser"
```

```bash
python manage.py makemigrations
# → Creates migration with CustomUser, Permission, and UserPermission
```

## Models contributed by other packages

A project's own models come from `INSTALLED_APPS`. A package built on the ORM
can also own tables every project using it has — `zeeb_api`'s auth tables are
one — through a **model provider**:

```python
from zeeb_orm.models.providers import register_model_provider


class BillingModels:
    app_labels = frozenset({"billing"})   # INSTALLED_APPS entries that stand for it

    def before_apps(self, project_root, settings):
        Plan._get_table()                 # nothing in the apps points at these first

    def after_apps(self, project_root, settings):
        Subscription._get_table()         # points at a project model (e.g. the user model)


register_model_provider("billing", BillingModels())
```

Declare it as an entry point too, so it is active before anything imports the
package:

```toml
[project.entry-points."zeeb_orm.model_providers"]
billing = "billing.orm_models:provider"
```

Model registration (makemigrations, migrate, `check`) calls every provider
around the app scan. A provider that raises stops it with
`ModelRegistrationError`, like an app whose models fail to import: a schema
diffed without those tables would drop them.

## Troubleshooting

### Pending Migrations Error

```
ERROR: Unapplied migrations detected. Run 'python manage.py migrate'
```

This appears when starting the server with pending migrations. Apply them:

```bash
python manage.py migrate
```

Or disable the check in settings:

```python
# settings.py
ENFORCE_MIGRATIONS = False
```

The check is skipped under `DEBUG` regardless. See
[Guarding against unapplied migrations](#guarding-against-unapplied-migrations)
for the underlying API.

### `MigrationError: Cannot add NOT NULL column ... with no default`

You added a `null=False` field to a model whose table already has rows, and the
field has no scalar `default`. Nothing was written — see
[Adding a NOT NULL column](#adding-a-not-null-column) for the three fixes.

### "No changes detected" when changes exist

If `makemigrations` says "No changes detected" but you've added or modified models, make sure:

1. Your app is listed in `INSTALLED_APPS` in `settings.py`
2. Your models are defined in the app's `models.py` file
3. Your models inherit from `Model` and are not abstract

```python
# settings.py
INSTALLED_APPS = [
    "apps.blog",   # ✓ App must be listed here
]
```

### App models not detected

If `makemigrations` doesn't find your app's models, check the console for warnings like:

```
UserWarning: Could not import models from app 'apps.myapp': No module named 'apps.myapp.models'
```

Common causes:
- Missing `models.py` in the app directory
- Missing `__init__.py` in the app or `apps/` directory
- Import errors within the models file (check the warning message)

### Adopting migrations in an existing project

If your database tables already exist but you have no migrations, create your
migrations first with `makemigrations`, then apply them with `--fake-initial`:

```bash
python manage.py makemigrations
python manage.py migrate --fake-initial
```

This skips the initial migration's schema operations (tables already exist) but
records it as applied so future migrations can build on it.

### Changing on_delete on an existing ForeignKey

New tables get the correct `ON DELETE` clause in their DDL automatically
(`CASCADE` → `ON DELETE CASCADE`, `SET_NULL` → `ON DELETE SET NULL`, etc.).
However, **changing `on_delete` on an existing ForeignKey is not autodetected**
and requires a manual migration: foreign key constraints can only be replaced
by dropping and re-adding them. (Unique-constraint and column changes *are*
auto-detected and applied via SQLite batch mode, but FK rebuilds across a
relation graph are left manual on purpose.)

In practice this matters less than it seems: `on_delete` behavior is enforced
in Python by the deletion collector, so updating the model definition changes
runtime behavior immediately. The database-level clause only acts as a backstop
for writes that bypass the ORM (and is not enforced on SQLite unless the
`foreign_keys` PRAGMA is enabled).

## Best Practices

### 1. Always Review Generated Migrations

```bash
# Generate
python manage.py makemigrations

# Review the file before applying
cat migrations/0001_initial.py
```

### 2. Use Descriptive Names

```bash
# Good
python manage.py makemigrations -n "add email verification fields to users"

# Bad
python manage.py makemigrations -n "update"
```

### 3. Test Migrations

```bash
# Apply
python manage.py migrate

# Rollback
python manage.py migrate --rollback 1

# Apply again
python manage.py migrate
```

### 4. Keep Migrations Small

- One logical change per migration
- Easier to review and rollback

### 5. Don't Edit Applied Migrations

Once a migration is applied in production, don't modify it. Create a new migration instead.

### 6. Commit Migrations to Version Control

Migrations are part of your codebase. Commit them with the model changes.

### 7. Squash periodically

As migrations accumulate, squash old migrations to keep the history manageable:

```bash
python manage.py squashmigrations 0001_initial 0020_add_comments -n "initial_squashed"
```

## Programmatic Usage

```python
from zeeb_orm.migrations import (
    makemigrations,
    migrate,
    rollback,
    showmigrations,
    squashmigrations,
    current,
    Migration,
    operations,
)

# Check for pending changes (raises SystemExit(1) if found)
makemigrations(check=True)

# Preview without writing
makemigrations(dry_run=True)

# Create migration
name = makemigrations(message='add new model')

# Preview what would run
migrate(plan=True)

# Apply all pending
migrate()

# Apply with fake-initial
migrate(fake_initial=True)

# Rollback one step
rollback(steps=1)

# Check status
showmigrations()

# Squash migrations
squashmigrations(start='0001_initial', end='0005_add_views', squashed_name='initial_squashed')
```

The engine underneath, for tools that want results rather than printed output:

```python
from zeeb_orm.migrations import executor
from zeeb_orm.migrations.autogen import make_migration

draft = make_migration("migrations", name="add_slug", accept_renames=False)
draft.name, draft.path, draft.operations   # path is None for dry_run=True
draft.report.possible_renames              # likely renames written as remove + add

result = executor.migrate_with_result(target="0003")   # a unique prefix works
result.applied, result.unapplied, result.target       # target: the full name

executor.rollback(1)          # names unapplied; executor.rollback_target(1) only plans
executor.rollback_with_result(1).target   # the target, worked out under the migrate lock
```

### Errors

All are `MigrationError` subclasses, importable from `zeeb_orm.migrations`:

| Error | Raised when |
|---|---|
| `UnknownMigrationError` | A `migrate` target matches no migration, or several (`.available`, `.candidates`). |
| `MigrationLayoutError` | Migrations sit in `migrations/versions/`, which the engine does not read. |
| `MigrationSerializationError` | An operation cannot be written to a file faithfully; nothing is written. |
| `IrreversibleError` | A rollback would need an irreversible operation; nothing is unapplied. |
| `MigrationStateError` | The applied migrations cannot be read from the database. |

### Where migration files live

Migration files live **flat** in `migrations/`, not under a `versions/`
subdirectory:

```
myproject/
└── migrations/
    ├── .gitkeep
    ├── 0001_initial.py
    └── 0002_add_article.py
```

`find_migration_files()` resolves them, and still finds a legacy
`migrations/versions/` directory if one exists — a flat file wins when both are
present. `migrate` and `makemigrations` never read `versions/`, so they refuse to
run while it holds migrations that `migrations/` does not, with
`MigrationLayoutError` — move the files up
(`mv migrations/versions/*.py migrations/`). `runserver` and `check` report the
same instead of calling the database up to date. Every programmatic command
takes `migrations_dir=` to work on a directory other than `migrations/`.

`init_migrations(directory="migrations")` creates the directory
programmatically:

```python
from zeeb_orm.migrations import init_migrations

init_migrations()                    # ./migrations
init_migrations("db/migrations")     # parent directories are created too
```

The path is resolved against the **current working directory**, not the
project root. An existing directory is left untouched; either way the function
prints what it did and returns `None`. Unlike `manage.py init` it writes no
`.gitkeep`. Calling it is optional — `makemigrations()` creates the directory
on its first run.

### Guarding against unapplied migrations

Serving traffic against a schema that does not match the models produces
confusing column errors deep in a query. These helpers let you fail fast
instead:

```python
from zeeb_orm import (
    MigrationError,
    MigrationState,
    check_migrations_applied,
    get_migration_state,
    require_migrations,
)

# True when the database is up to date. With raise_on_pending=True (the
# default) it raises MigrationError instead of returning False.
check_migrations_applied(raise_on_pending=False)

# The full picture, for a health endpoint or a startup log line
state: MigrationState = get_migration_state()
state.has_migrations_dir   # bool
state.total_migrations     # int
state.applied_migrations   # int
state.pending_migrations   # int
state.current_revision     # str | None — where the database is
state.head_revision        # str | None — where the code says it should be
```

`require_migrations` is a decorator for entry points that must not run against
a stale schema:

```python
@require_migrations
async def nightly_report():
    ...   # raises MigrationError if anything is pending
```

Both `check_migrations_applied()` and `get_migration_state()` accept
`project_root=` and `db_url=` to inspect a project other than the current one.

#### When the database cannot be read

If the applied migrations cannot be read — the database is unreachable, the
credentials are wrong, the driver is missing — `get_migration_state()` raises
`MigrationStateError` rather than reporting every migration as pending (which
would send you off to "apply" migrations against a database you cannot reach).
The message names the database with its password masked and the underlying
error; the original exception is chained as `__cause__`.

`MigrationStateError` is a subclass of `MigrationError`, so code that already
catches `MigrationError` — and `require_migrations` — fails closed on it.
`check_migrations_applied()` propagates it even with `raise_on_pending=False`:
an unreadable database is not the same answer as "migrations pending". Catch it
when you need to tell the two apart:

```python
from zeeb_orm import check_migrations_applied
from zeeb_orm.migrations import MigrationStateError

try:
    up_to_date = check_migrations_applied(raise_on_pending=False)
except MigrationStateError as exc:
    print(f"database unreachable: {exc}")
else:
    print("up to date" if up_to_date else "migrations pending")
```

A project whose `settings.py` does not import raises `SettingsImportError`
instead (see [Project discovery](../configuration/database.md#project-discovery)).

The `ENFORCE_MIGRATIONS` setting (default `True`) applies the same check at
startup outside `DEBUG` — see
[Settings](../configuration/settings.md).
