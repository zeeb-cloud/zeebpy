# Migrations

Zeeb provides Django-style migrations — no Alembic config files, no revision hashes, just clean numbered Python files.

## Overview

Migrations track changes to your models and apply them to the database. The workflow is:

1. **Make changes** to your models
2. **Generate migration** with `makemigrations`
3. **Apply migration** with `migrate`

## Getting Started

### Create First Migration

After defining models, generate the initial migration:

```bash
python manage.py makemigrations
```

Output:
```
Checking for model changes in installed apps:
  - blog
  - users

Migrations for 'all apps':
  0001_initial.py
    - Create model Author
    - Create model Post
```

No `init` step needed — `makemigrations` creates the `migrations/` directory automatically.

### Apply Migrations

```bash
python manage.py migrate
```

Output:
```
Running migrations:
  Applying 0001_initial... OK
```

## Commands

### makemigrations

Generate migrations from model changes.

```bash
# Generate for all apps
python manage.py makemigrations

# Generate with custom name
python manage.py makemigrations -n "add user profile"

# Generate empty migration (for manual edits)
python manage.py makemigrations --empty

# Check for pending changes (CI/CD) — exits 1 if changes are detected, no file written
python manage.py makemigrations --check

# Preview what would be generated without writing any files
python manage.py makemigrations --dry-run
```

**Options:**
| Option | Description |
|--------|-------------|
| `-n, --name` | Migration name/description |
| `--empty` | Create empty migration |
| `--check` | Exit with status 1 if model changes are detected. No file is written. Ideal for CI pipelines to enforce committed migrations. |
| `--dry-run` | Show what migration would be created without writing any files. |

### migrate

Apply migrations to the database.

```bash
# Apply all pending migrations
python manage.py migrate

# Apply to specific migration
python manage.py migrate 0001

# Roll back all migrations
python manage.py migrate zero

# Rollback N migrations
python manage.py migrate --rollback 1

# Mark as applied without running
python manage.py migrate --fake

# Skip initial migration when tables already exist (adopting migrations in existing project)
python manage.py migrate --fake-initial

# Show what would be applied without running anything
python manage.py migrate --plan
```

**Options:**
| Option | Description |
|--------|-------------|
| `migration` | Target migration name (optional) |
| `--rollback N` | Roll back N migrations |
| `--fake` | Mark as applied without executing |
| `--fake-initial` | Skip the first migration if its tables already exist |
| `--plan` | Print the list of migrations that would run, without executing them |

### showmigrations

Display migration status.

```bash
python manage.py showmigrations
```

Output:
```
 [X] 0001_initial
 [X] 0002_add_user_profile
 [ ] 0003_add_comments
```

**Status indicators:**
- `[X]` - Applied
- `[ ]` - Pending

### squashmigrations

Squash a range of migrations into a single optimized file.

```bash
# Squash migrations 0001 through 0005 into one file
python manage.py squashmigrations 0001_initial 0005_add_views

# With a custom name
python manage.py squashmigrations 0001_initial 0005_add_views -n "initial_to_add_views"

# Skip the optimizer (keep all operations as-is)
python manage.py squashmigrations 0001_initial 0005_add_views --no-optimize
```

**Options:**
| Option | Description |
|--------|-------------|
| `start` | First migration in the range (inclusive) |
| `end` | Last migration in the range (inclusive) |
| `-n, --name` | Name for the squashed migration file |
| `--no-optimize` | Disable the optimizer — keep all operations |

The squashed file includes a comment listing which migrations it replaces.
After deploying the squashed migration everywhere, the original files may be deleted.

## Migration File Format

Migration files are clean Python with a `Migration` class:

```python
# migrations/0001_initial.py
"""Create model Post

Generated by Zeeb ORM on 2024-01-15 12:34
"""

import sqlalchemy as sa
from zeeb_orm.migrations import Migration, operations


class Migration(Migration):

    initial = True

    dependencies = []

    operations = [
        operations.CreateModel(
            name='Post',
            table='posts',
            columns=[
                sa.Column('id', sa.Uuid(), nullable=False),
                sa.Column('title', sa.String(200), nullable=False),
                sa.Column('content', sa.Text(), nullable=False),
                sa.Column('created_at', sa.DateTime(), nullable=True),
            ],
            primary_key=['id'],
        ),
    ]
```

### Migration class options

| Attribute | Default | Description |
|-----------|---------|-------------|
| `initial` | `False` | Mark this as the initial migration |
| `dependencies` | `[]` | List of migration names this depends on |
| `atomic` | `True` | Wrap all operations in a single database transaction |

### Pre/post migrate hooks

Override `pre_migrate` and/or `post_migrate` on your `Migration` class to run
custom code before or after the migration's operations execute:

```python
class Migration(Migration):

    dependencies = ['0002_add_slug']

    operations = [
        operations.AddField(
            model_name='Post',
            table='posts',
            name='slug',
            column=sa.Column('slug', sa.String(200), nullable=True),
        ),
    ]

    def pre_migrate(self, connection):
        """Called before operations run."""
        print("About to add slug column…")

    def post_migrate(self, connection):
        """Called after operations run (populate data, etc.)."""
        from sqlalchemy import text
        connection.execute(text(
            "UPDATE posts SET slug = LOWER(REPLACE(title, ' ', '-')) WHERE slug IS NULL"
        ))
```

### Non-atomic migrations

Set `atomic = False` to run outside a transaction — required for some DDL
statements that cannot run inside a transaction, e.g.
`CREATE INDEX CONCURRENTLY` on PostgreSQL:

```python
class Migration(Migration):

    atomic = False  # Cannot run inside a transaction

    operations = [
        operations.RunSQL(
            sql="CREATE INDEX CONCURRENTLY idx_posts_slug ON posts (slug)",
            reverse_sql="DROP INDEX IF EXISTS idx_posts_slug",
        ),
    ]
```

### Available Operations

| Operation | Description |
|-----------|-------------|
| `CreateModel` | Create a new database table |
| `DeleteModel` | Drop a database table |
| `AddField` | Add a column to an existing table |
| `RemoveField` | Remove a column from a table |
| `AlterField` | Change a column's type, nullable, etc. |
| `RenameModel` | Rename a table |
| `RenameField` | Rename a column |
| `AddIndex` | Create an index |
| `RemoveIndex` | Drop an index |
| `AddConstraint` | Add a named constraint (unique, check, …) |
| `RemoveConstraint` | Drop a named constraint |
| `RunSQL` | Execute raw SQL |
| `RunPython` | Execute a Python callable |

#### RenameModel

```python
operations.RenameModel(
    old_name='Post',
    new_name='Article',
    old_table='posts',
    new_table='articles',
)
```

Reversal: renames back to the original table name.

#### RenameField

```python
operations.RenameField(
    model_name='Post',
    table='posts',
    old_name='body',
    new_name='content',
)
```

Reversal: renames back to the original column name.

#### RemoveField (with reversal)

Pass the `field` argument to enable reversal (the column can be re-added on
rollback):

```python
operations.RemoveField(
    model_name='Post',
    table='posts',
    name='legacy_id',
    field=sa.Column('legacy_id', sa.Integer(), nullable=True),
)
```

Without `field`, the operation is irreversible.

#### AlterField (with reversal)

Pass `old_column_type` and/or `old_nullable` to enable reversal:

```python
operations.AlterField(
    model_name='Post',
    table='posts',
    name='views',
    column_type=sa.BigInteger(),
    old_column_type=sa.Integer(),  # needed for reversal
)
```

#### AddConstraint / RemoveConstraint

```python
operations.AddConstraint(
    model_name='Post',
    table='posts',
    constraint=sa.UniqueConstraint('slug', name='uq_posts_slug'),
)

operations.RemoveConstraint(
    model_name='Post',
    table='posts',
    name='uq_posts_slug',
)
```

### Auto-detection

Zeeb compares your current model definitions against the **state described by existing migration files** (not the live database). This means:

- Running `makemigrations` multiple times without model changes produces no duplicate migrations
- You don't need to apply migrations before generating new ones
- Changes are detected reliably regardless of the database state

Zeeb auto-detects these changes:

- **Tables**: Create, drop
- **Columns**: Add, drop, alter type
- **Indexes**: Create, drop
- **Nullability**: Changes to nullable

## Common Workflows

### Adding a Field

```python
# 1. Add field to model
class Post(Model):
    title = fields.CharField(max_length=200)
    content = fields.TextField()
    views = fields.IntegerField(default=0)  # New field
```

```bash
# 2. Generate migration
python manage.py makemigrations -n "add views to posts"

# 3. Apply
python manage.py migrate
```

### Removing a Field

```python
# 1. Remove field from model
class Post(Model):
    title = fields.CharField(max_length=200)
    content = fields.TextField()
    # views field removed
```

```bash
# 2. Generate migration
python manage.py makemigrations -n "remove views from posts"

# 3. Apply
python manage.py migrate
```

### Data Migrations

For data transformations, create an empty migration:

```bash
python manage.py makemigrations --empty -n "populate slug from title"
```

```python
# Edit the generated migration
import sqlalchemy as sa
from zeeb_orm.migrations import Migration, operations


class Migration(Migration):

    dependencies = ['0002_add_slug']

    operations = [
        operations.RunSQL(
            sql="""
                UPDATE posts
                SET slug = LOWER(REPLACE(title, ' ', '-'))
                WHERE slug IS NULL
            """,
            reverse_sql=None,
        ),
    ]
```

### Adding a Relationship

```python
# 1. Add ForeignKey
class Post(Model):
    title = fields.CharField(max_length=200)
    author = fields.ForeignKey(
        "Author",
        on_delete="CASCADE",
        null=True,  # Allow null for existing rows
    )
```

```bash
# 2. Generate and apply
python manage.py makemigrations -n "add author to posts"
python manage.py migrate
```

### CI/CD — Enforcing Committed Migrations

Add a step in CI to ensure all model changes have a corresponding migration:

```yaml
# .github/workflows/ci.yml
- name: Check for uncommitted migrations
  run: python manage.py makemigrations --check
```

This exits with status 1 when any model changes are not yet represented by a
migration file, failing the pipeline.

### Squashing Old Migrations

After many iterations, squash migrations 0001–0010 into one file:

```bash
python manage.py squashmigrations 0001_initial 0010_add_comments
```

The optimizer automatically combines operations (e.g. `CreateModel` + `AddField`
on the same table become a single `CreateModel`), resulting in a compact file.

## Migration Tracking

Applied migrations are tracked in the `zeeb_migrations` table in your database. This table is automatically created when you first run `migrate`.

```sql
-- The tracking table
SELECT * FROM zeeb_migrations;
-- id | name              | applied_at
-- 1  | 0001_initial      | 2024-01-15T12:34:56
-- 2  | 0002_add_profile  | 2024-01-16T09:00:00
```

## Custom User Models

When using a custom user model via `AUTH_USER_MODEL`, the migration system
automatically handles the `UserPermission` table.  Its foreign key points to
whichever user model is configured — no extra setup needed.

```python
# settings.py
AUTH_USER_MODEL = "apps.accounts.CustomUser"
```

```bash
python manage.py makemigrations
# → Creates migration with CustomUser, Permission, and UserPermission
```

## Troubleshooting

### Pending Migrations Error

```
ERROR: Unapplied migrations detected. Run 'python manage.py migrate'
```

This appears when starting the server with pending migrations. Apply them:

```bash
python manage.py migrate
```

Or disable the check in settings:

```python
# settings.py
CHECK_MIGRATIONS_ON_STARTUP = False
```

### "No changes detected" when changes exist

If `makemigrations` says "No changes detected" but you've added or modified models, make sure:

1. Your app is listed in `INSTALLED_APPS` in `settings.py`
2. Your models are defined in the app's `models.py` file
3. Your models inherit from `Model` and are not abstract

```python
# settings.py
INSTALLED_APPS = [
    "apps.blog",   # ✓ App must be listed here
]
```

### App models not detected

If `makemigrations` doesn't find your app's models, check the console for warnings like:

```
UserWarning: Could not import models from app 'apps.myapp': No module named 'apps.myapp.models'
```

Common causes:
- Missing `models.py` in the app directory
- Missing `__init__.py` in the app or `apps/` directory
- Import errors within the models file (check the warning message)

### Adopting migrations in an existing project

If your database tables already exist but you have no migrations, create your
migrations first with `makemigrations`, then apply them with `--fake-initial`:

```bash
python manage.py makemigrations
python manage.py migrate --fake-initial
```

This skips the initial migration's schema operations (tables already exist) but
records it as applied so future migrations can build on it.

## Best Practices

### 1. Always Review Generated Migrations

```bash
# Generate
python manage.py makemigrations

# Review the file before applying
cat migrations/0001_initial.py
```

### 2. Use Descriptive Names

```bash
# Good
python manage.py makemigrations -n "add email verification fields to users"

# Bad
python manage.py makemigrations -n "update"
```

### 3. Test Migrations

```bash
# Apply
python manage.py migrate

# Rollback
python manage.py migrate --rollback 1

# Apply again
python manage.py migrate
```

### 4. Keep Migrations Small

- One logical change per migration
- Easier to review and rollback

### 5. Don't Edit Applied Migrations

Once a migration is applied in production, don't modify it. Create a new migration instead.

### 6. Commit Migrations to Version Control

Migrations are part of your codebase. Commit them with the model changes.

### 7. Squash periodically

As migrations accumulate, squash old migrations to keep the history manageable:

```bash
python manage.py squashmigrations 0001_initial 0020_add_comments -n "initial_squashed"
```

## Programmatic Usage

```python
from zeeb_orm.migrations import (
    makemigrations,
    migrate,
    rollback,
    showmigrations,
    squashmigrations,
    current,
    Migration,
    operations,
)

# Check for pending changes (raises SystemExit(1) if found)
makemigrations(check=True)

# Preview without writing
makemigrations(dry_run=True)

# Create migration
name = makemigrations(message='add new model')

# Preview what would run
migrate(plan=True)

# Apply all pending
migrate()

# Apply with fake-initial
migrate(fake_initial=True)

# Rollback one step
rollback(steps=1)

# Check status
showmigrations()

# Squash migrations
squashmigrations(start='0001_initial', end='0005_add_views', squashed_name='initial_squashed')
```
