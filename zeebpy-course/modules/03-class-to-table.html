From a Python Class to a Database Table

We are on the ground floor now — the Database Brain (zeeb_orm). Let us watch a class become a real table.

Who actually builds the table — and when?

In Module 1 you saw class User(Model) turn into a real table. But a plain Python class has no idea what a database is.

🏛️
The metaphor: a blueprint becoming a building

Your Python class is the blueprint. A hidden construction crew reads it the instant the class is defined. The database table is the finished building. And migrations are the renovation permits: a logbook of every change you make over time.

📄
The blueprint — your model

A Python class listing the fields you want to store.

🏗️
The construction crew — the metaclass

Runs the moment the class is defined and assembles the table plan.

🗄️
The finished building — the table

A real grid in the database, ready to hold your data.

Each field is one column

Inside the model, every line declares a column. You are not just naming things — each field also sets a data type and its rules.

CODE 
    name = fields.CharField(max_length=100)
    email = fields.EmailField(unique=True)
    age = fields.IntegerField(null=True)
    is_active = fields.BooleanField(default=True)
    bio = fields.TextField(null=True)
    created_at = fields.DateTimeField(auto_now_add=True)
PLAIN ENGLISH

name becomes a text column, at most 100 characters.

email becomes a text column that must be unique across the whole table.

age becomes a whole-number column that is allowed to be empty.

is_active becomes a true/false column, defaulting to true.

bio becomes a long-text column, optional.

created_at becomes a date-and-time column that stamps itself automatically.

Meet the construction crew: the metaclass

A special piece of machinery called a metaclass (ModelBase) runs the instant your class is defined. It scans the class for fields, collects them, and assembles the table blueprint.

CODE 
        # Collect fields from this class
        for attr_name, attr_value in list(namespace.items()):
            if isinstance(attr_value, Field):
                attr_value.contribute_to_class(new_class, attr_name)
                fields.append(attr_value)
                if attr_value.primary_key:
                    has_pk = True
                    new_class._meta.pk = attr_value
                    new_class._meta.pk_name = attr_name

Declarative, not imperative

Notice you never wrote CREATE TABLE. You declared what a User is, and the metaclass figured out the step-by-step build for you. Migrations do the exact same thing for changes to that model.

The migration loop: how a change reaches the database

Changing your model does not change the database by itself. Two commands close the gap: makemigrations writes down the change, then migrate applies it.

How does the detective know what changed?

You might expect it to peek at the live database. It does something smarter and safer instead — it replays the history of every past migration into a throwaway copy and compares against that.

🔍
From the source (autodetector.py)

"Compare current model state against existing migration state and return operations. This is the core of makemigrations — it detects what changed. Instead of comparing against the live database (which would re-detect already-migrated changes if migrations have not been applied yet), this replays all existing migration files into an in-memory SQLite database and compares the model metadata against that state."

schema The overall shape of your database: its tables and columns.
in-memory SQLite A tiny throwaway database that lives only in memory — used just for this comparison, then discarded.

The single most common beginner bug

⚠️
The "no such column" trap

Whenever you change a model, you must run makemigrations then migrate. Forget it, and the app crashes with errors like no such column: phone — because the model changed but the real table never did. This is the #1 thing vibe coders get stuck on.

1
Change your model

Add, remove, or edit a field in models.py.

2
Run makemigrations

The change gets written into a new dated file.

3
Run migrate

That file is applied — the real table finally matches your model.
