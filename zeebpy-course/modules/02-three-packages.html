The Cast of Characters

Three separate packages, stacked like floors of a building — and one strict rule about who is allowed to call whom.

Meet the whole family

Last module you met one of the three characters — the ORM, which saved a record for you. It turns out it has two siblings.

zeebpy isn't one giant blob of code. It's three separate packages stacked like the floors of a building, connected by a strict one-way elevator: the top floor can call down to the floors below, but no floor can ever call up.

🏢
The metaphor: a three-story building

Each floor has exactly one job and depends only on the floors beneath it. The elevator runs one way — down. Keep that picture in your head; the whole module hangs on it.

The three characters

Each package is a character with one clear job. Their colors stay the same for the rest of the course, so you'll always know who's speaking.

🧠

zeeb_orm

The Database Brain. Knows how to talk to the database. Turns Python classes into tables and queries into SQL. Depends on nothing above it.

🏢

zeeb_api

The Web Front Desk. Faces the outside world. Turns your data into a REST API — web addresses other apps can call. Uses the ORM to fetch and save data.

🤖

zeeb_agents

The Robot Helpers. ~43 helper functions an AI assistant can call to scaffold code, run migrations, inspect the database. Sits on top and uses both siblings.

The one-way rule, in real code

Here's the top of example_api.py. When one package uses another, it imports it. Watch which direction the imports point.

    Model, fields, Q,
    configure, setup_database, close_all_connections,
)

# Zeeb API imports
from zeeb_api import (
    ModelSerializer, ModelViewSet, DefaultRouter,
    ...
)
PLAIN ENGLISH

The comment marks where the database-layer tools come from.

From zeeb_orm we borrow the building blocks for data: Model, fields, and query tools.

…the pieces that set up and talk to the database.

 

The comment marks the web-layer tools.

From zeeb_api we borrow the tools that turn that data into a web API.

Notice the direction: the API file reaches down into the ORM. The ORM never reaches up into the API — that is the one-way elevator rule.

Why this matters to you

💡
Separation of concerns

Splitting a system into layers that each do one job — and only depend downward — is one of software's most important ideas. It's why you can change how data is stored without touching how the web API looks.

When you can name which layer owns what, you can steer an AI precisely and debug faster:

🧠
Data is wrong?

Look in the ORM — the Database Brain owns how data is fetched and stored.

🏢
A web request 404s?

Look in the API — the Web Front Desk owns the web addresses.

🤖
Scaffolding or migrations?

That's the Robot Helpers on the top floor.

Engineers call this whole idea separation of concerns. Say it to an AI — "put this database logic in the ORM layer, not the API layer" — and you'll get sharper results.

Check your intuition

No memorizing — just think through where things live.
