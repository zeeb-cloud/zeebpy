01

What zeebpy Is

And what really happens when you save one record

One line. No database commands.

You write a single line of Python to save a new user:

✨
The magic line

await User.objects.create(name="Alice", ...) — no SQL, no raw database commands. Here is the journey that one line takes under the hood.

So what is zeebpy?

zeebpy is a framework for building the back end of a web app. You write Python classes that describe your data, and zeebpy hands you a working database plus a ready-made REST API almost for free.

What you get out of the box

🗄️
A database

A permanent home for your app data — no setup rituals required

🌐
A REST API

Web addresses that let phones and websites read and change your data

📦
Migrations

Safe, tracked updates to your data structure as your app grows

🔐
Auth

Built-in login, passwords, and permissions so you do not build them yourself

The interpreter in the booth

Picture a simultaneous interpreter at the United Nations. You speak Python; the database only speaks SQL. zeebpy sits in the booth and translates, live, in both directions.

You never have to learn the database's language — you just talk, and the interpreter handles the rest. That interpreter has a real name: an ORM (Object-Relational Mapper).

💡
Declarative vs. plumbing

You declared what a User looks like. You never wrote code to open a database connection, build a SQL string, or juggle data types. That gap is exactly what a framework fills for you.

Step 1 — Describe your data

First you write a model: a class that spells out what a User is. Each line is a field — one piece of information you want to keep.

CODE 
class User(Model):
    """User model with basic fields."""
    name = fields.CharField(max_length=100)
    email = fields.EmailField(unique=True)
    age = fields.IntegerField(null=True)
    is_active = fields.BooleanField(default=True)
    bio = fields.TextField(null=True)
    created_at = fields.DateTimeField(auto_now_add=True)

    class Meta:
        table_name = "users"
        ordering = ["-created_at"]
PLAIN ENGLISH

Describe a kind of thing we want to store — a User.

A human-readable note about what this is.

Every user has a name — up to 100 letters long.

…and an email, which must be unique — no two users can share one.

…and an age, which is optional (null=True means "can be blank").

…and an on/off switch for whether the account is active — on by default.

…and a free-text bio, also optional.

…and a timestamp that fills itself in the moment the user is created.

Meta is a settings panel for this model.

Store these in a database table literally named "users".

When listing users, show newest first (the minus means "descending").

Step 2 — Save an actual user

Now you fill in the blanks and hit save. The word await tells your code to wait for the database to finish, because that work is async.

CODE 
alice = await User.objects.create(
    name="Alice Smith",
    email="alice@example.com",
    age=28,
    bio="Software engineer"
)
PLAIN ENGLISH

Ask the User "front desk" (objects) to create a new user, and wait for it to finish (await).

Her name is Alice Smith.

Her email is alice@example.com.

She is 28.

Her bio says "Software engineer." zeebpy writes all of this into the database as one new row.

Engineers call this whole idea separation of concerns. Say it to an AI — "put this database logic in the ORM layer, not the API layer" — and you'll get sharper results.

How does the detective know what changed?

You might expect it to peek at the live database. It does something smarter and safer instead — it replays the history of every past migration into a throwaway copy and compares against that.

🔍
From the source (autodetector.py)

"Compare current model state against existing migration state and return operations. This is the core of makemigrations — it detects what changed. Instead of comparing against the live database (which would re-detect already-migrated changes if migrations have not been applied yet), this replays all existing migration files into an in-memory SQLite database and compares the model metadata against that state."

schema The overall shape of your database: its tables and columns.
in-memory SQLite A tiny throwaway database that lives only in memory — used just for this comparison, then discarded.

Asking the Database Questions

Your data lives in a table now. Time to ask it questions — without writing a single line of SQL.

You are just writing down the question

Think of refining filters on a shopping site. You tick "under $30," then "in stock," then "newest first." Nothing loads. The page only fetches results when you finally press the button.

The hook

User.objects.filter(age__lt=30) — you have not asked the database anything yet. You have only written down the question. It runs the moment you await it, and not a nanosecond before.

A zeebpy QuerySet works exactly like those shopping filters: you stack conditions, and the database is only bothered when you press "go."

From plain words to a database question

Here is real code from example_basic.py. Each line is a lookup that zeebpy translates into a WHERE clause.

CODE 
    # Filter users
    active_users = await User.objects.filter(is_active=True)

    # Filter with lookups
    young_users = await User.objects.filter(age__lt=30)

    adults = await User.objects.filter(age__gte=25, age__lte=40)
PLAIN ENGLISH

Find users matching a condition.

Ask for users whose is_active switch is on → SQL: WHERE is_active = true.

 

Conditions can be comparisons, not just equals.

age__lt=30 means "age less than 30" → SQL: WHERE age < 30. The __lt is the magic word for "less than."

 

age__gte=25, age__lte=40 means "at least 25 AND at most 40" → SQL: WHERE age >= 25 AND age <= 40.

Those age__lt=30 pairs are keyword arguments — the name carries both the field and the comparison, the value is what to match.

Why nothing runs yet: filter hands back a copy

This is the heart of the trick, from zeeb_orm/query/queryset.py. When you call .filter(), zeebpy does not touch the database — it makes a fresh clone of your question and hands that back.

CODE 
        self._check_combinator("filter")
        clone = self._clone()
        if args:
            for arg in args:
                if isinstance(arg, Q):
                    clone._filters.append(arg)
        if kwargs:
            clone._filters.append(Q(**kwargs))
        return clone
PLAIN ENGLISH

First a safety check that filtering is allowed here.

Make a fresh copy of the question — never modify the original.

If you passed any Q objects…

…go through them one by one…

 

…and add each as a new condition on the copy.

If you passed plain keywords like age__lt=30…

…bundle them into a condition and add that too.

Hand back the copy. Notice: it talked to no database. It just remembered your condition and returned a new question.

Because each .filter() returns a brand-new copy, QuerySets are chainable: you can stack .filter().filter() forever, and every earlier question stays untouched.

The exact moment it runs

💡
Lazy evaluation

Building a query costs nothing — only await (or looping over it) actually triggers the database. This is a deliberate design: you can pass an unfinished query around, tack on more filters, and run it just once at the very end.

Deep in queryset.py lives the switch that fires only when you put await in front of a query. This is where a saved-up question finally becomes real rows.

CODE 
    def __await__(self) -> Any:
        """Allow awaiting QuerySet directly to get list of results."""
        return self._fetch_all().__await__()
PLAIN ENGLISH

This special method fires only when you put await in front of the query.

Awaiting the query is what turns it into a real list of results.

Now — and only now — it runs _fetch_all, which sends the SQL to the database and brings back the rows. This is what it means to execute a query.

Combining conditions with Q

Plain filters are joined with AND. When you need OR or NOT, you reach for a Q object. These four examples come straight from the code's own documentation in zeeb_orm/query/q.py.

Q(name='John') A single plain condition, ready to reuse or combine.
Q(age__gte=18) & Q(age__lte=65) & = AND — both must be true: at least 18 and at most 65.
Q(status='active') | Q(status='pending') | = OR — either one counts: active or pending.
~Q(deleted=True) ~ = NOT — flips it: everything that is not deleted.

06

Guarding the Door

How the API knows who you are, and what you are allowed to do.

Should anyone be able to delete a book?

In Module 5 you learned to create and delete books over the web. That is exactly why we need a lock on the door. Should any stranger be able to call DELETE /books/5/? Obviously not.

So how does the API know who you are, and what you are allowed to do? Meet the bouncer.

🎟️
The nightclub metaphor

The bouncer checks your ID at the door. Your wristband proves you were already checked, so you do not re-show ID at every bar. The guest list says who gets into the VIP room. The capacity limit caps how many people pour in at once.

💂
Bouncer = the middleware

Checks your token on every single request before anything else runs.

🎟️
Wristband = the token

Tamper-proof proof of who you are, so you do not log in again on every click.

📋
Guest list = permissions

Even a checked-in guest is not allowed everywhere. Are you allowed to delete this book?

🚦
Capacity limit = throttling

Only so many requests per minute, so no one can flood the club.

Four guards, four questions

Every protected request passes through up to four checks. Each answers one plain question.

🪪

Authentication

Who are you? You prove it once with a login, and get a signed token.

💂

Middleware

Is your pass real? The bouncer runs on every request, decodes the token, and attaches the user.

📋

Permissions

What may you do? The guest list decides if this user may perform this action.

🚦

Throttling

How often? A capacity limit caps how many requests anyone can fire per minute.

🔑
Authentication vs. authorization

Authentication asks who are you. Authorization asks what may you do. They sound alike but are two separate checks — and mixing them up is a classic security bug.

Stamping the wristband

When you log in successfully, the server builds a wristband: a small bundle of facts, sealed with a signature. Here is that exact moment in zeeb_api/auth/jwt.py.

CODE 
    payload = {
        "sub": str(user_id),
        "type": "access",
        "exp": now + timedelta(minutes=config.access_token_expire_minutes),
        "iat": now,
        "jti": str(uuid.uuid4()),
    }

    if config.issuer:
        payload["iss"] = config.issuer
    if config.audience:
        payload["aud"] = config.audience
    if claims:
        payload["claims"] = claims

    return jwt.encode(payload, config.secret_key, algorithm=config.algorithm)
PLAIN ENGLISH

Start building the wristband — a small bundle of facts.

sub = who this is (the user id).

type = what kind of pass this is (an access pass).

exp = when it expires — wristbands do not last forever.

iat = when it was issued.

jti = a unique serial number for this exact token.

Optionally stamp who issued it and who it is for.

Optionally attach extra facts.

Finally, seal it with a secret signature. Anyone can read the facts, but no one can forge or change them without the secret.

💡
Why a signed token beats a session lookup

The wristband carries its own proof. The server does not have to remember you or look you up in a database on every click — it just re-reads the sealed facts. Engineers call this stateless auth.

The bouncer on every request

Before your request reaches the code that deletes a book, the middleware inspects it. It looks in the header for a Bearer token.

CODE 
        request.state.user = None

        # Try to extract and validate token
        auth_header = request.headers.get("Authorization")
        if auth_header and auth_header.startswith("Bearer "):
            token = auth_header[7:]  # Remove "Bearer " prefix

            try:
                payload = decode_token(token, token_type="access")

                # Load user (custom loader or default)
                if self.user_loader:
                    request.state.user = await self.user_loader(payload)
                else:
                    request.state.user = AuthenticatedUser(payload)
PLAIN ENGLISH

Assume nobody until proven otherwise — start with no user.

Look for a token on the request.

Check the request for an Authorization header.

If it starts with the word Bearer, the token follows it...

...snip off the Bearer prefix to get the raw token.

Try to open and verify the wristband...

...decode it and check the signature and expiry.

If a custom user-lookup is set, use it to fetch the full user...

...otherwise build a lightweight user straight from the token facts. Either way, request.state.user is now set for everything downstream.

Where it can stop early

If the token were missing or expired, the bouncer stops it at step 3 and the browser gets a 401 Unauthorized. If the user simply lacked permission, the guest list stops it at step 5 with a 403 Forbidden.

The guest list, in code

A permission is just a yes/no function that runs before the action. Here is the simplest one — are you logged in at all? — from zeeb_api/permissions/base.py.

CODE 
    async def has_permission(self, request: Request, view: ViewSet) -> bool:
        # Check if user is authenticated
        # FastAPI stores user in request.state after authentication
        user = getattr(request.state, "user", None)
        return user is not None and getattr(user, "is_authenticated", True)
PLAIN ENGLISH

This yes/no gate runs before the action.

It looks at who the bouncer already identified.

Grab the user the middleware attached (or nothing, if none).

Allow the action only if there is a user and they count as logged in. No wristband, no entry.

Richer permission classes build on this same shape — checking whether you are an admin, whether you own the record, or whether you hold a specific role.

The whole thing rests on one secret

The wristband is only forgery-proof because the seal uses a secret key that only the server knows. If anyone could guess that secret, they could forge a wristband for any user — including an admin.

⚠️
zeebpy refuses to start with a default secret

When DEBUG is false, zeebpy will not boot with the built-in placeholder secret — it raises an error instead. This is a safety net so a demo secret never sneaks into production. Never ship a default or guessable secret.

From the human's door to the robot's help desk

In Module 6 you saw the whole framework a human uses. Now meet the layer an AI uses.

zeebpy ships about 43 helper functions an AI assistant can call to scaffold apps, run migrations, and inspect your database. Every single one obeys two unbreakable rules.

🏢
The metaphor: a help desk with one standard form

Imagine a help desk where every request — no matter how it goes — comes back on the same tidy slip: done ✓ or not done ✗, here's why, here's the data. No confusing pile of errors ever gets thrown back at you across the counter.

Two rules, and they're a masterclass in careful design

📋
Rule 1 — Uniform result

Every function hands back the exact same shape: AgentResult(success, message, data). Callers never have to guess.

🛡️
Rule 2 — Never raises

A decorator catches any error and turns it into a friendly failed result instead of crashing the caller.

Rule 1 up close: one shape, every time

Whatever you ask for, the slip has the same three fields. That predictability is the whole point.

success Did it work? A simple true / false. This is what the caller checks first.
message A human-readable sentence — "Created app 'blog'." or "Project folder not found."
data A bag of structured details (file paths, row counts, names). May be empty — but it's always there.
💡
Why a fixed shape matters

Because the return value never changes shape, the code calling 43 different functions can be written once and trusted everywhere. This is called a contract.

Rule 2 up close: the safety net that never lets go

This is the real wrapper. It looks long, but it's doing one calm thing: catch everything, hand back a slip.

CODE 
        @functools.wraps(fn)
        async def wrapper(*args: Any, **kwargs: Any) -> AgentResult:
            try:
                if needs_root:
                    bound = signature.bind(*args, **kwargs)
                    bound.apply_defaults()
                    given = bound.arguments.get("project_root")
                    if isinstance(given, str):
                        given = Path(given)
                    try:
                        bound.arguments["project_root"] = require_project_root(given)
                    except RuntimeError as exc:
                        logger.info("%s failed: %s", fn.__qualname__, exc)
                        return fail(str(exc), code="no_project_root")
                    args, kwargs = bound.args, bound.kwargs
                return await fn(*args, **kwargs)
            except AgentError as exc:
                # Expected, targeted failure — no traceback needed.
                logger.info("%s failed: %s", fn.__qualname__, exc)
                return exc.result
            except FileNotFoundError as exc:
                logger.exception("%s failed", fn.__qualname__)
                return fail(f"FileNotFoundError: {exc}", code="file_not_found")
            except PermissionError as exc:
                logger.exception("%s failed", fn.__qualname__)
                return fail(f"PermissionError: {exc}", code="permission_denied")
            except Exception as exc:
                logger.exception("%s failed", fn.__qualname__)
                return AgentResult(
                    success=False, message=f"{type(exc).__name__}: {exc}"
                )
PLAIN ENGLISH

Wrap the real function so callers still see its name and docs — but with our safety net around the whole body.

try = attempt the real work, ready to catch anything that goes wrong.

First, resolve and sanity-check the project folder. If that step fails, hand back a clean failure slip — don't crash.

Now run the actual function and return whatever it produced.

If it raised an expected error, return the friendly failure it already prepared.

If a file was missing, return a "file not found" slip — not a crash.

If a permission was denied, return a "permission denied" slip.

And the catch-all: any other error at all becomes an AgentResult with success = False. Nothing ever escapes as an exception.

🪤
The whole trick in one sentence

No matter what breaks — missing file, denied permission, or a bug nobody predicted — the last net catches it and turns it into a normal result. The caller cannot be crashed.
